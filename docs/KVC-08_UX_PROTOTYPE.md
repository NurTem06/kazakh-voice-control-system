# KVC-8 — UX Prototype and User Interaction Scenarios

## 1. Introduction

This document presents the user experience (UX) design and interactive interface prototype for **Qazaq Voice**, an intelligent Kazakh-language voice control system for Windows 11.

The purpose of the prototype is to demonstrate how users will interact with the proposed application, provide commands, view recognition results, and recover from errors.

The prototype supports the design decisions described in:

- `KVC-01_PROJECT_PROPOSAL.md`
- `KVC-02_RELEVANCE_EVIDENCE.md`
- `KVC-06_REQUIREMENTS_SPECIFICATION.md`
- `KVC-07_ARCHITECTURE.md`

**Current development stage:** Interactive user interface prototype.

The prototype is not a fully functional voice assistant. It does not record microphone audio, perform neural speech recognition, or execute real Windows operating-system commands.

## 2. UX Design Objectives

The interface is designed around six primary objectives.

1. **Simple interaction:** Users should be able to understand the interface without extensive technical knowledge.
2. **Kazakh-language accessibility:** Primary controls, example commands, and interaction feedback should be available in Kazakh.
3. **Clear system status:** Users should understand whether the assistant is idle, listening, processing, or displaying a result.
4. **Alternative input:** Users should have a text-based interaction method when voice input is unavailable or inconvenient.
5. **Safe error handling:** Unsupported commands should produce understandable feedback without unintended system actions.
6. **Consistent feedback:** The interface should display the submitted command, interpreted intent, and simulated execution outcome.

These objectives reflect the planned application requirements and preliminary findings from the user needs assessment in KVC-2.

### 3.2 Implemented Prototype Interactions

The interactive prototype currently includes:

- A Windows-style application layout.
- Sidebar navigation.
- Kazakh-language command examples.
- A simulated microphone activation button.
- A text input field.
- A command submission button.
- Simulated processing feedback.
- Basic keyword-based demonstration of intent recognition.
- Displays for submitted text and recognized intent.
- Simulated success and error notifications.
- A history panel containing up to five recent demo commands.
- History clearing and interface reset controls.
- A help dialog explaining the prototype's limitations.

All demonstrated command results are generated by the browser-based prototype.

## 5. User Interface States

The prototype demonstrates five main interaction states.

| State | Description | User Feedback |
|---|---|---|
| Ready | No command is being processed | The interface invites the user to select or enter a command |
| Listening | The user activates the demo listening control | The interface displays a listening indication; no audio is recorded |
| Processing | A text command is submitted | The interface displays a processing indicator |
| Success | A command matches one of the demonstrated supported intents | The interface displays the intent and a simulated successful result |
| Error | A command is unsupported or not recognized by the demo matcher | The interface displays an error message and allows another attempt |

### 5.1 Ready State

The application displays the main assistant panel, command examples, and text input field.

The user can select a sample command or enter a custom phrase.

### 5.2 Listening State

Selecting the demo listening control changes the interface to a listening state.

This interaction demonstrates the intended appearance of active voice recording.

**The prototype does not access the microphone or capture audio.**

### 5.3 Processing State

When a text command is submitted, the interface temporarily displays processing feedback.

This simulated delay is a UI animation. It is not a measured neural ASR inference time or real command execution latency.

### 5.4 Success State

If the entered text matches the demonstration's supported command patterns, the interface displays a corresponding intent and success message.

The intended Windows action is described, but not executed.

### 5.5 Error State

If the submitted text does not match a supported demonstration command, the interface displays an unsupported-command message.

For example, entering **"Компьютерді өшір"** demonstrates refusal of a shutdown request.

This is a UX error scenario, not a completed security validation of a production command executor.

## 6. User Interaction Scenarios

Eight scenarios were selected to demonstrate the intended interaction flows.

| ID | Example Kazakh Command | Intended Intent | Prototype Result |
|---|---|---|---|
| UX-01 | Браузерді аш | `open_browser` | Simulated browser launch |
| UX-02 | Калькуляторды аш | `open_calculator` | Simulated Calculator launch |
| UX-03 | Блокнотты аш | `open_notepad` | Simulated Notepad launch |
| UX-04 | Дыбысты көтер | `volume_up` | Simulated volume increase |
| UX-05 | Дыбысты азайт | `volume_down` | Simulated volume decrease |
| UX-06 | Уақытты көрсет | `show_time` | Demonstration of time-display feedback |
| UX-07 | Google-дан Астананы ізде | `web_search` | Simulated web-search request |
| UX-08 | Компьютерді өшір | `UNKNOWN` | Unsupported-command error |

**Implementation note:** The demo now uses `volume_up` and `volume_down`, consistent with KVC-6. The UI error identifier `unsupported_command` remains distinct from the planned classifier label `UNKNOWN`.

### 6.1 Normal Scenario — Open Calculator

1. The user opens the Qazaq Voice prototype.
2. The user selects the "Калькуляторды аш" example or types the phrase.
3. The prototype displays a processing state.
4. The JavaScript demonstration identifies the Calculator intent.
5. The interface displays a simulated success result.
6. The interaction appears in the recent command history.

**Current result:** The UX flow is demonstrated. Windows Calculator is not actually launched.

### 6.2 Alternative Scenario — Text Command

1. The user opens the interface.
2. The user enters "Блокнотты аш" into the command field.
3. The user clicks the submit button or presses Enter.
4. The interface displays the interpreted command.
5. A simulated result is shown.

This scenario demonstrates the proposed non-voice fallback.

### 6.3 Error Scenario — Unsupported Command

1. The user enters "Компьютерді өшір".
2. The prototype processes the text.
3. No supported demonstration intent is matched.
4. The interface displays an error state.
5. The submitted phrase and failed result appear in the command history.
6. The user can enter another command or reset the interface.

**Current result:** The prototype demonstrates the intended refusal message. No Windows action takes place because the HTML demonstration has no operating-system execution capability.

## 7. User Needs and Design Rationale

The initial questionnaire documented in KVC-2 provided preliminary information about potential user preferences.

Respondents mentioned basic operations, including application launching and volume adjustment.

The questionnaire also highlighted the importance of retaining visual or manual controls when voice recognition fails.

These observations informed several interface decisions.

| User Need or Concern | UX Design Response |
|---|---|
| Interest in simple Windows operations | Visible examples for launching applications and changing volume |
| Potential speech recognition errors | Clear success and failure states |
| Need for manual alternatives | Text-based command input |
| Uncertainty about recognized speech | Separate text and intent result displays |
| Difficulty understanding interface behavior | Visible system status and short feedback messages |
| Need to retry after an error | Reset control and reusable command input |

The questionnaire was a preliminary needs assessment, not a usability test of the completed interface.

Therefore, it does not establish that the prototype is easy to use for all intended user groups.

## 8. Usability and Accessibility Considerations

The UX design considers the following principles:

- Use readable interface labels.
- Keep the primary interaction control prominent.
- Clearly distinguish successful and failed operations.
- Avoid relying exclusively on speech interaction.
- Provide visible command information.
- Keep errors recoverable.
- Use a consistent layout across interface states.
- Avoid presenting simulated outcomes as real system actions.

### Limitations

The following characteristics have not yet been formally verified:

- Full keyboard navigation.
- Screen-reader accessibility.
- Accessibility of all control labels.
- Color contrast compliance.
- Text scaling at different display settings.
- Usability for older adults.
- Usability for people with specific disabilities.
- User comprehension of error and privacy messages.

These aspects require a later accessibility audit and user testing.

## 11. Demonstration Procedure

The prototype can be demonstrated using the following procedure.

1. Open `prototype/index.html` in a supported web browser.
2. Show the initial assistant dashboard and example commands.
3. Select "Демо тыңдау" to demonstrate the listening state.
4. Stop the listening demonstration.
5. Select "Калькуляторды аш" to demonstrate a supported command.
6. Observe the processing, intent, simulated result, and command history.
7. Enter "Компьютерді өшір" to demonstrate the unsupported-command state.
8. Clear the command history or reset the interface.
9. Explain that the speech recognition model and Windows execution module will be integrated during later development.

The optional Windows launch helper opens the same HTML interface in an application-style browser window. It does not enable native Windows command execution.

## 13. Conclusion

The KVC-8 prototype demonstrates the proposed user interaction experience for Qazaq Voice.

It illustrates how a user may provide Kazakh commands, receive feedback, view interpreted intents, and recover from unsupported-command errors.

The interface incorporates preliminary user needs related to basic Windows operations and the availability of visual or manual input alternatives.

The existing prototype is suitable for discussing the intended UX design during the first checkpoint.

However, it does not establish that neural speech recognition, Windows execution, command safety, or accessibility requirements have already been implemented or verified.

These capabilities remain part of the project's subsequent development and evaluation stages.
