# KVC-9 — Verification and Evaluation Plan

## 1. Introduction

This document describes the planned verification and evaluation methodology for **Qazaq Voice**, an intelligent Kazakh-language voice control system designed for Windows 11.

The purpose of this plan is to define how the future implementation will be tested for functional correctness, speech recognition accuracy, command execution reliability, performance, usability, security, and compatibility.

The evaluation methodology is based on the requirements established in `KVC-06_REQUIREMENTS_SPECIFICATION.md` and the architecture proposed in `KVC-07_ARCHITECTURE.md`.

**Current status:** Evaluation plan prepared. The integrated system has not yet been implemented or experimentally tested.

All numerical targets in this document are proposed engineering objectives, not achieved results.

## 2. Evaluation Objectives

The evaluation has seven main objectives:

1. Measure the accuracy of Kazakh-language speech recognition.
2. Evaluate whether recognized phrases are correctly classified into supported intents.
3. Verify the execution of approved Windows commands.
4. Measure end-to-end response latency.
5. Confirm that unsupported or potentially dangerous commands do not trigger unauthorized actions.
6. Verify user interface feedback, manual input alternatives, and error recovery.
7. Assess compatibility, stability, and privacy-related behavior on Windows 11.

The evaluation must distinguish errors introduced by individual components from failures in the complete application.

## 3. System Under Evaluation

The proposed processing pipeline is:

**Voice Input → Audio Preprocessing → Neural ASR → Text Normalization → Intent Recognition → Action Validator → Windows Executor → User Feedback**

A second input path is provided for typed commands:

**Text Input → Text Normalization → Intent Recognition → Action Validator → Windows Executor → User Feedback**

The system is planned to support seven predefined intents.

| Intent ID | Example Kazakh Phrase | Expected Windows Action |
|---|---|---|
| `open_browser` | Браузерді аш | Open the default browser |
| `open_calculator` | Калькуляторды аш | Open Calculator |
| `open_notepad` | Блокнотты аш | Open Notepad |
| `volume_up` | Дыбысты көтер | Increase system output volume |
| `volume_down` | Дыбысты азайт | Decrease system output volume |
| `show_time` | Уақытты көрсет | Display the local system time |
| `web_search` | Google-дан Астананы ізде | Open a validated web search |

Unsupported inputs must be classified as `UNKNOWN` and must not trigger unapproved Windows actions.

## 4. Evaluation Metrics

### 4.1 Word Error Rate (WER)

Word Error Rate measures the difference between the reference transcription and the text generated by the ASR model.

**Formula:**

WER = (S + D + I) / N

Where:

- S — number of substituted words.
- D — number of deleted words.
- I — number of inserted words.
- N — number of words in the reference transcription.

**Interpretation:** Lower WER indicates fewer transcription errors.

WER will be calculated after applying a consistent, documented normalization procedure to reference and predicted transcripts.

The team must document punctuation handling, casing, whitespace normalization, and treatment of Kazakh-specific characters.

### 4.2 Character Error Rate (CER)

Character Error Rate measures transcription differences at the character level.

**Formula:**

CER = (S + D + I) / N

For CER, substitutions, deletions, insertions, and reference length are counted in characters instead of words.

CER is particularly useful when analyzing recognition mistakes involving Kazakh spelling and specific characters.

**Interpretation:** Lower CER indicates fewer character-level errors.

### 4.3 Intent Recognition Accuracy

Intent Recognition Accuracy measures the proportion of test inputs assigned to the correct intent.

**Formula:**

Intent Accuracy = Correct Intent Predictions / Total Evaluated Inputs × 100%

Example:

If the system correctly classifies 90 out of 100 test commands:

Intent Accuracy = 90%

This is an illustrative calculation, **not an experimental result from Qazaq Voice**.

The evaluation set must include both supported intents and unsupported commands labeled as `UNKNOWN`.

The report should also include a confusion matrix and macro-averaged F1 score to identify errors hidden by unequal class frequencies.

**Proposed target:** At least 85% intent accuracy.

This target requires confirmation through pilot testing and supervisor review.

### 4.4 Windows Command Execution Success Rate

This metric evaluates whether the Windows Executor correctly performs an approved action.

**Formula:**

Execution Success Rate = Successfully Executed Approved Actions / Validated Action Attempts × 100%

This metric must be measured using known, correctly classified intent inputs.

It isolates the reliability of Windows execution from errors introduced by ASR.

Examples include:

- Calculator opens after receiving `open_calculator`.
- System volume increases by the predefined amount after `volume_up`.
- Current local time is displayed after `show_time`.

**Proposed target:** At least 95% successful execution under defined valid test conditions.

### 4.5 End-to-End Task Success Rate

End-to-End Task Success measures the success of the complete processing pipeline, beginning with a spoken command and ending with the observed intended Windows action.

**Formula:**

End-to-End Task Success = Successfully Completed Spoken Tasks / Total Valid Spoken Task Attempts × 100%

Unlike the execution success rate, this metric includes possible failures in:

- Audio capture.
- Speech recognition.
- Text normalization.
- Intent recognition.
- Command validation.
- Windows execution.

The end-to-end success rate must be reported separately from execution success.

A numerical acceptance target will be finalized after the initial pilot evaluation.

### 4.6 Response Latency

End-to-end latency is measured from the moment the user finishes speaking until the intended Windows action is observed or an error is presented.

The following statistics will be recorded:

- Median latency (p50).
- 95th-percentile latency (p95).
- Maximum observed latency.
- Number of evaluated requests.

**Proposed target:** Median end-to-end latency of no more than 4 seconds on documented Windows 11 hardware.

The p95 latency must also be reported, but no final p95 acceptance threshold has been established.

The latency of typed commands should be measured separately because typed input bypasses microphone recording and neural ASR.

### 4.7 False Action Rate

False Action Rate evaluates whether unsupported or misrecognized inputs trigger unintended Windows actions.

**Formula:**

False Action Rate = Negative Test Inputs Causing an Unintended Action / Total Negative Test Inputs × 100%

Negative inputs include:

- Unsupported requests.
- Dangerous commands.
- Ambiguous instructions.
- Malformed parameters.
- Incorrectly recognized speech.
- Injection-like text.

**Expected safety criterion:** No unauthorized Windows action should occur during the defined negative test suite.

Passing a finite test suite does not prove that the system is immune to all possible unsafe inputs.

## 5. ASR Technology Evaluation

### 5.1 Candidate Models

The proposed ASR evaluation will initially consider two model approaches.

| Candidate | Technology | Evaluation Purpose |
|---|---|---|
| ASR-B1 | Whisper multilingual [R5] | Baseline pretrained multilingual speech recognition |
| ASR-B2 | Suitable Kazakh-adapted XLS-R checkpoint [R6] | Evaluate the potential benefits of language-specific adaptation |

Additional models may be included if compatible checkpoints and sufficient computing resources are available.

The exact model identifiers, configurations, and licenses must be recorded before testing.

### 5.2 Relevant Speech Resources

Potential research resources include:

- Kazakh Speech Corpus (KSC) [R2].
- Kazakh Speech Corpus 2 (KSC2) [R3].
- Multilingual evaluation practices described by FLEURS [R7].

These sources provide possible methodological and data resources.

However, existing research datasets may not adequately represent short Windows voice commands.

Therefore, the team should consider a separate command-oriented evaluation set.

### 5.3 Fair Comparison Conditions

All ASR candidates must be tested under comparable conditions.

The evaluation should control:

- Test dataset and transcription references.
- Audio sample rate and input format.
- Hardware configuration.
- Model inference settings.
- Background noise categories.
- Speaker distribution.
- Text-normalization rules.
- Latency measurement methodology.

If model-specific preprocessing is required, the differences must be documented.

Model comparison must not be based solely on published scores obtained from unrelated datasets.

## 6. Test Dataset Design

### 6.1 Dataset Composition

The planned evaluation dataset should contain examples of all seven supported intent categories and a separate set of unsupported inputs.

| Category | Examples |
|---|---|
| Application launching | Open browser, Calculator, Notepad |
| Audio control | Increase or decrease volume |
| Information request | Display current time |
| Web search | Search for a specific topic |
| Unsupported commands | Shutdown, delete files, arbitrary terminal commands |
| Linguistic variation | Alternative Kazakh expressions for the same intent |
| Code-switching | Kazakh speech containing Russian or English words |
| Acoustic variation | Quiet and noisy recording conditions |

The final number of recordings and speakers will depend on available resources.

The test-set size must be reported rather than assumed.

### 6.2 Data Collection and Consent

Any newly recorded speech used for evaluation must be collected with appropriate participant consent.

The team should avoid collecting unnecessary personal or sensitive information.

Audio files must be stored securely, and their use must follow the agreed research and privacy procedures.

The questionnaire results collected for KVC-2 provide preliminary user preferences but **do not constitute an ASR evaluation dataset**.

### 6.3 Dataset Splitting

If training or fine-tuning is performed, the data should be divided into training, validation, and test sets.

Speakers should be separated between these sets where feasible to reduce speaker-related data leakage.

The final test set must not be used to tune the model.

### 6.4 Linguistic and Acoustic Variation

The evaluation should consider:

- Regional Kazakh pronunciation differences.
- Speakers with different levels of Kazakh proficiency.
- Kazakh–Russian code-switching.
- Short commands and alternative wording.
- Background conversations and environmental noise.
- Microphone differences.

These are proposed evaluation dimensions. Their effects on the final system have not yet been measured.

## 7. Test Case Matrix

The first 12 test cases preserve the original KVC-9 evaluation plan.

Additional tests have been introduced to improve coverage of the requirements defined in KVC-6.

### 7.1 Core Functional Tests

| ID | Test Case | Input / Setup | Expected Result |
|---|---|---|---|
| TC-01 | Start and stop microphone capture | Microphone access permitted | Listening state activates and deactivates correctly |
| TC-02 | Kazakh transcription | Recorded Kazakh speech with reference text | Transcript is returned or a recoverable ASR error is reported |
| TC-03 | Intent parsing | "Калькуляторды аш" | Intent `open_calculator` is returned |
| TC-04 | Browser launch | Validated `open_browser` intent | Default browser opens |
| TC-05 | Calculator and Notepad | Validated `open_calculator` and `open_notepad` intents | Correct applications open |
| TC-06 | Volume adjustment | Validated `volume_up` and `volume_down` intents | Volume changes by the approved bounded increment |
| TC-07 | Time display and web search | Validated `show_time` and `web_search` intents | Correct time is displayed or a validated search URL opens |

### 7.2 Error Handling and Security Tests

| ID | Test Case | Input / Setup | Expected Result |
|---|---|---|---|
| TC-08 | Microphone permission denied | Disable microphone permission in Windows | Application displays a recoverable error without crashing |
| TC-09 | Noise and speech variation | Held-out recordings with different acoustic or linguistic conditions | WER/CER and error categories are reported |
| TC-10 | Unsupported command | "Компьютерді өшір" | `UNKNOWN`; no Windows action is executed |
| TC-11 | ASR failure or timeout | Simulate an unavailable or failing ASR adapter | Application displays an error without crashing or executing an action |
| TC-12 | Command injection attempt | Input containing shell commands or untrusted executable text | Input is rejected or treated as unsupported; no shell execution occurs |

### 7.3 Extended Tests

| ID | Test Case | Input / Setup | Expected Result |
|---|---|---|---|
| TC-13 | Text-based command fallback | Enter "Блокнотты аш" through the UI | Command passes through the same intent and validation pipeline without microphone access |
| TC-14 | Session history | Submit several supported commands, then clear history | Recent interactions are displayed and can be cleared |
| TC-15 | Privacy and recording behavior | Start and stop recording; inspect application data handling | Recording is explicitly controlled and raw audio is not persistently stored by default |
| TC-16 | Keyboard and visual interaction | Navigate essential controls without speech input | Essential controls are operable and system status is visible |
| TC-17 | Offline ASR operation | Disconnect network after local setup | Offline speech recognition works if implemented; otherwise feature is documented as unavailable |
| TC-18 | Windows compatibility | Run the application on documented Windows 11 x64 configuration | Required functions operate without compatibility failures |
| TC-19 | Modular component verification | Replace ASR output with predefined text inputs | Intent recognition, validation, and action mapping can be tested independently of microphone input |

### 7.4 Test Execution Status

**Current status: NOT TESTED**

The complete neural ASR-to-Windows-action system has not yet been implemented.

The HTML UX prototype from KVC-8 demonstrates selected interface states and simulated commands, but it does not provide evidence of successful real Windows command execution.

Actual test results must be recorded only after the relevant implementation has been executed and evaluated.

## 8. Security Verification

Security testing is critical because the application interacts with operating-system functions.

### 8.1 Approved Command Verification

Only intents explicitly included in the allowed command set may reach the Windows Executor.

The system must reject unknown intent identifiers.

### 8.2 Arbitrary Command Execution

Speech transcriptions and text commands must never be passed directly into PowerShell, Command Prompt, or another command shell.

### 8.3 Unsupported Operations

The test set should include attempts to:

- Shut down the computer.
- Delete files.
- Execute terminal commands.
- Modify privileged system settings.
- Invoke unsupported applications.
- Perform actions outside the command allowlist.

**Expected result:** No unapproved operating-system action occurs.

### 8.4 Web Search Validation

Web search queries must be treated as text data.

Queries must be validated and URL-encoded before being passed to a browser.

The application must not interpret web-search contents as executable operating-system commands.

### 8.5 Error Recovery

After rejecting an unsupported request, the application should remain responsive and allow another input.

## 9. Usability Evaluation

The usability evaluation will examine whether users can understand the interface and recover from interaction failures.

The planned criteria include:

- Visibility of microphone status.
- Clarity of recognized text.
- Clarity of success and error feedback.
- Availability of text-based input.
- Ability to repeat a failed interaction.
- Keyboard accessibility of essential controls.
- Understandability of supported commands.
- Ability to clear session history.

A later usability study should include representative users and predefined tasks.

Potential benefits for older adults and people with disabilities must not be described as validated unless appropriately designed testing is performed.

## 12. Reproducibility and Evidence Collection

For each evaluation run, the team should record:

1. Test date and evaluator.
2. Application version or Git commit identifier.
3. Operating-system version and build.
4. CPU, GPU, RAM, and microphone configuration.
5. ASR model and checkpoint version.
6. Dataset source, license, and number of samples.
7. Number of speakers and data-splitting methodology.
8. Command categories and test-case identifiers.
9. Text-normalization settings.
10. Actual measurements and failure descriptions.
11. Relevant screenshots or execution logs.
12. Known limitations and deviations from the testing protocol.

Where appropriate, results should be summarized using per-class counts, confidence intervals, and observed error distributions.

The raw evaluation data must be retained securely, with appropriate treatment of participant recordings.

## 13. Planned Evaluation Stages

### Stage 1 — Component Verification

Test text normalization, intent recognition, action validation, and approved command mappings independently.

### Stage 2 — ASR Benchmarking

Evaluate compatible multilingual and Kazakh-adapted ASR checkpoints using the same held-out test data.

Measure WER, CER, and inference performance.

### Stage 3 — Windows Integration Testing

Connect validated intent outputs to approved Windows operations.

Verify correct execution and failure handling.

### Stage 4 — End-to-End Evaluation

Test the complete pipeline using spoken Kazakh commands.

Measure command success, recognition accuracy, and latency.

### Stage 5 — Safety and Usability Testing

Evaluate unsupported commands, malformed parameters, privacy-related behavior, user feedback, and manual fallback options.

### Stage 6 — Reporting and Review

Prepare a reproducible results report, document limitations, and review findings with the project supervisor.

## 15. Conclusion

The verification and evaluation plan establishes a structured methodology for assessing Qazaq Voice.

It defines metrics for speech recognition, intent classification, Windows command execution, end-to-end task success, latency, security, usability, and compatibility.

The plan contains 19 test cases, including the original functional and security scenarios and additional tests for alternative input, history, privacy, accessibility, offline operation, and modularity.

The evaluation methodology distinguishes individual component performance from the reliability of the complete voice-to-action pipeline.

All targets remain provisional until the relevant software has been implemented, experimental results have been collected, and the criteria have been reviewed with the supervisor.
